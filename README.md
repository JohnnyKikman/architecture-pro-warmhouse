# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

API монолитного приложения содержит следующие методы:

- **GET /api/v1/sensors** - Получает список устройств (датчиков), получая от устройства актуальное состояние
- **GET /api/v1/sensors/:id** - Получает данные о конкретном устройстве по его ID, получая от устройства его актуальное состояние
- **GET /api/v1/sensors/temperature/:location** - Получает актуальные данные о температуре с конкретного устройства по его метке местоположения 
- **POST /api/v1/sensors** - Создает в БД новый датчик
- **PUT /api/v1/sensors/:id** - Обновляет в БД данные о существующем датчике по ID
- **DELETE /api/v1/sensors/:id** - Удаляет из БД существующий датчик по ID
- **PATCH /api/v1/sensors/:id/value** - Вручную обновляет в БД желаемое значение температуры

*Поскольку отсутствует разделение на классы устройства и датчика, предполагается, что в рамках задания понятия "датчик" и "устройство" равнозначны.*

Таким образом, функциональность монолитного приложения следующая:

**Работа со списком устройств:**

- API позволяет подключать к системе новые устройства, обновлять о них информацию, а также удалять их
- При этом эти методы доступны только специалисту по подключению устройств, конечный пользователь не может вызвать их через веб-интерфейс 

**Управление отоплением:**

- Пользователи могут задавать желаемое значение температуры отопления
- Управление происходит пользователем через веб-интерфейс
- В отсутствие явных команд к устройству отопления, считаем, что метода задания температуры отопления "под капотом" также прокидывает эту информацию до самого устройства

**Мониторинг температуры:**

- Пользователи могут проверять текущую температуру по датчику в синхронном режиме
- Получение информации пользователем происходит через веб-интерфейс

### 2. Анализ архитектуры монолитного приложения

Перечислите здесь основные особенности текущего приложения: какой язык программирования используется, какая база данных, как организовано взаимодействие между компонентами и так далее.

- **Язык программирования**: Go
- **База данных**: PostgreSQL
- **Архитектура**: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- **Взаимодействие**: Синхронное, через HTTP-запросы с телами в виде JSON-сообщений, запросы обрабатываются последовательно.
- **Масштабируемость**: Ограничена, так как монолит сложно масштабировать по частям.
- **Развертывание**: Требует остановки всего приложения. Остановка приводит к недоступности всего функционала.
- **Отказоустойчивость**: Низкая. Проблемы с работой приложения на промышленной среде приводят к недоступности всего функционала - как считывания информации с датчиков, так и управления отоплением, а также регистрации устройств.
- **Безопасность**: Низкая. Учет пользователей отсутствует. Любой пользователь может просмотреть информацию и управлять любым устройством, зная его ID и/или местоположение, что делает их уязвимыми для атак.
- **Расширяемость**: API и структура БД теоретически поддерживает добавление новых видов устройств (с помощью полей с типом устройства и единицей изменения).

### 3. Определение доменов и границы контекстов

- **Домен: Личный кабинет**
  - Контекст: Регистрация пользователя
  - Контекст: Проверка принадлежности устройства пользователю
- **Домен: Управление устройствами**
  - Поддомен: Работа со списком устройств
    - Контекст: Регистрация устройства в системе
    - Контекст: Отключение устройства от системы
    - Контекст: Работа с группами устройств
  - Поддомен: Управление состоянием устройств
    - Контекст: Обновление состояния устройства (температурой, освещением и т.д.)
- **Домен: Сбор данных с датчиков**
  - Контекст: Получение данных с датчиков


### **4. Проблемы монолитного решения**

- Невозможна самостоятельная регистрация устройств в системе, требуется вызов специалиста компании, что ведет к дороговизне установки.
- Единая точка отказа - если приложение остановлено, недоступна вся функциональность системы, а не только какая-то часть.
- Масштабирование возможно только всего приложения целиком: к примеру, если вырастет число запросов информации с датчиков, то придется масштабировать заодно управление устройствами и их регистрацию/удаление.
- Синхронное взаимодействие от сервера к устройствам приводит к тому, что только пользователь инициирует любое взаимодействие с устройстами, т.е. само устройство не может обновлять информацию о себе (например, сообщить о невозможности отрегулировать температуру).
- Отсутствие видимых механизмов безопасности ведет к тому, что злоумышленники, зная список ID устройств, могут свободно управлять всеми устройствами всех клиентов, или же один клиент может управлять устройством другого без его согласия.
- Изменения в одной части монолита могут вызвать неожиданные баги в других частях, что потребует дополнительных ресурсов для тестирования и рискует вызвать остановку всего сервиса в случае ошибок на промышленной среде.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
